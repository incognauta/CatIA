## 1. REGLAS DE COMPORTAMIENTO GENERAL

### 1.1 Toma de Decisiones - REGLA CRÍTICA ✅

**ANTES de implementar cualquier cambio arquitectónico o decisión importante, el Asistente DEBE:**

1. **Presentar opciones claras**: Mínimo 2-3 opciones con pros/contras de cada una
2. **Mostrar impacto**: Describir cómo afectará cada opción al proyecto (timeline, complejidad, futuro)
3. **Documentar supuestos**: Qué se está asumiendo en cada opción
4. **ESPERAR aprobación del usuario**: No proceder hasta el usuario haya elegido

**Ejemplo correcto:**

```
Necesito decidir sobre la estructura de DocumentVersion.

OPCIÓN A (Simple - velocidad):
├─ Pros: MVP rápido, sin complejidad
├─ Contras: Difícil migrar a PDF después
└─ Impacto: +1 semana en Fase 4B

OPCIÓN B (Robusto - escalado):
├─ Pros: OCR ready, versionado, auditoria
├─ Contras: Más código inicial
└─ Impacto: +2 días ahora, -1 semana en Fase 5

¿Cuál prefieres?
```

**Ejemplo INCORRECTO:**

```
Voy a implementar DocumentVersion con versioning.
```

---

### 1.2 Cambios a Codebase

- **No crear PRs automáticas**: Solo editar archivos si el usuario lo solicita explícitamente
- **Informar antes de cambios mayores**: Mostrar lista de archivos a cambiar y por qué
- **Mantener coherencia**: Seguir patrones ya establecidos en el proyecto
- **Actualizar docs**: Cualquier cambio al código debe reflejarse en docs/

---

### 1.3 Comunicación

- **Ser conciso**: Máximo 3-4 párrafos para explicaciones simples
- **Usar tablas/listas**: Para comparaciones y tracking
- **Links a documentación**: Referenciar archivos específicos cuando sea relevante
- **Confirmación de acciones**: Antes de operaciones destructivas, preguntar

## 2. REGLAS DE DOCUMENTACIÓN

### 2.1 Dónde documentar qué

| Tipo de Documento      | Ubicación                                                     | Responsable         | Frecuencia                            |
| ---------------------- | ------------------------------------------------------------- | ------------------- | ------------------------------------- |
| Objetivos, requisitos  | `objetivo.md`                                                 | Usuario             | Actualizar si cambian requisitos      |
| Decisiones técnicas    | `docs/Progreso/04_decisiones_tecnicas.md`                     | Asistente + Usuario | Después de cada decisión importante   |
| Cronograma, tracking   | `docs/Planificacion y contexto/03_tracking_plan.md`           | Asistente           | Actualizar después de cada sesión     |
| Pasos ejecutados, logs | `docs/Progreso/09_pasos_decisiones.md`                        | Asistente           | Después de completar tarea importante |
| Arquitectura           | `docs/Progreso/05_arquitectura_general.md`                    | Usuario             | Cambios en estructura general         |
| Estado de fases        | `docs/Progreso/01_fase1_estado.md`, `11_fase4_mvp_hibrido.md` | Asistente           | Fin de cada fase                      |

### 2.2 Qué incluir en documentación

Cada documento importante debe tener:

```markdown
# [Título del documento]

> **Estado:** [ACTIVO|PENDIENTE|ARCHIVED]  
> **Última actualización:** DD de MMM de AAAA  
> **Responsable:** [Usuario/Asistente/Ambos]

## Contexto

[Por qué existe este documento]

## Contenido

[Lo sustancial]

## Impacto/Notas

[Para próximas sesiones]
```

### 2.3 Archivos a EVITAR crear

- ❌ Resúmenes diarios (info va a tracking_plan.md)
- ❌ Archivos temporales de notas (son para memory, no docs/)
- ❌ Duplicados de información ya en otros archivos

## 3. REGLAS TÉCNICAS DE DESARROLLO

### 3.1 Antes de editar código

- [ ] Revisar `docs/Progreso/09_pasos_decisiones.md` para contexto
- [ ] Consultar `docs/Progreso/06_estructura_backend.md` para patrones
- [ ] Verificar que no existe el código ya (búsqueda en `grep_search`)
- [ ] Preguntar al usuario si la dirección es correcta

### 3.2 Después de editar código

- [ ] Ejecutar `python manage.py check` (sin errores)
- [ ] Si hay migraciones: `python manage.py migrate` y reportar resultado
- [ ] Actualizar tracking (fecha + qué se hizo)
- [ ] Linkear archivos modificados en la documentación

### 3.3 Estructura por App (Django)

Cada app debe mantener:

```
apps/<nombre>/
  ├── models.py         (entidades)
  ├── serializers.py    (validación/respuesta)
  ├── views.py          (endpoints)
  ├── urls.py           (rutas)
  ├── services.py       (lógica compleja)
  ├── permissions.py    (controles de acceso)
  ├── admin.py          (panel admin)
  └── tests.py          (mínimo 1 test por modelo)
```

## 5. PASOS PARA COMENZAR UNA SESIÓN

Cuando inicies una nueva sesión con el Asistente:

### 5.1 Proporciona contexto

```
Contexto para esta sesión:
- ¿Qué quieres hacer? (ej: "Iniciar Fase 4A - Modelos")
- ¿Qué archivos consultaste ya? (ej: "Leí objetivo.md y tracking_plan.md")
- ¿Hay bloqueadores? (ej: "Necesito decidir sobre versioning de documentos")
- ¿Cuál es el timeout? (ej: "Tengo 30 minutos disponibles")
```

### 5.2 El Asistente DEBE

1. Leer `docs/Progreso/09_pasos_decisiones.md` para contexto histórico
2. Leer `docs/Planificacion y contexto/03_tracking_plan.md` para estado actual
3. Revisar `.instructions.md` (este archivo) para cumplir reglas
4. Confirmar entendimiento del estado actual al usuario

### 5.3 Fin de sesión

Actualizar:

- `docs/Planificacion y contexto/03_tracking_plan.md` con resumen de cambios
- `docs/Progreso/09_pasos_decisiones.md` si se hizo algo importante
- Estado de fase actual en archivos correspondientes

## 6. PREGUNTAS FRECUENTES

### ¿Qué hago si el usuario no da opciones claramente?

→ Generar 2-3 opciones automáticamente, presentar, y esperar decisión.

### ¿Qué pasa si descubro un problema en la arquitectura?

→ Documentar en `04_decisiones_tecnicas.md` como "Problema encontrado", explicar, proponer soluciones, y esperar aprobación.

### ¿Cuándo actualizar tracking_plan.md?

→ Después de CADA cambio significativo o fin de sesión.

### ¿Puedo eliminar un archivo de docs?

→ NO. Marcar como `[ARCHIVED]` en el estado y explicar por qué en el documento.

### ¿Cómo manejo cambios que afectan múltiples archivos?

→ Usar `multi_replace_string_in_file` en una sola operación, documentar en tracking.
